## 5. Booking classification decision table

Inputs: `_booking_id`, `_flow ∈ {destination_charge_v1, separate_charges_v1}`, optional `_reason`.

| Booking state | `_flow` argument | Outcome | SQLSTATE / note |
|---|---|---|---|
| does not exist | any | reject | `P0002` |
| `payment_intent_id IS NULL` | any | reject (ambiguous) | `22023` |
| bad `currency` (length ≠ 3) | any | reject | `22023` |
| `provider_stripe_account_id IS NULL` | `destination_charge_v1` | reject | `22023` |
| `payment_flow_version IS NULL` | `destination_charge_v1` (with stripe acct) | classify, audit-log, return `destination_charge_v1` | ok |
| `payment_flow_version IS NULL` | `separate_charges_v1` | classify, audit-log, return `separate_charges_v1` | ok |
| `payment_flow_version = X` | same `X` | idempotent replay, return `X`, no audit-log | ok |
| `payment_flow_version = X` | different `Y` | reject | `55000` |
| concurrent classifier wins with same `X` | `X` | replay path returns `X` | ok |
| concurrent classifier wins with different `X` | `Y` | reject | `40001` |
| direct SQL `UPDATE bookings SET payment_flow_version=…` | n/a | rejected by Step 1 immutability trigger `bookings_payment_flow_version_immutable_trg` | as before |

Backfill: **no bulk backfill executed.** Existing bookings retain
`payment_flow_version = NULL`. Only classification via this RPC (called
from future ingestion code) assigns a version, and only based on
authoritative booking facts. New bookings are NOT auto-classified as
`separate_charges_v1` merely because the flag exists.

## 7. Idempotency-key formats and payload fingerprint rules

**Client-supplied component of the key.** Each ingestion primitive builds
the idempotency key deterministically from Stripe or booking identifiers
(see table above). Callers never assemble raw ledger keys.

**Server-derived fingerprint.** For every candidate insert,
`_ledger_payload_fingerprint` computes:

```
sha256(
  jsonb {
    event_type,
    event_id,
    currency,
    booking_id,
    provider_user_id,
    entries = _ledger_normalize_entries(entries)
  } :: text
)  →  hex
```

**Normalization (`_ledger_normalize_entries`).** Every entry is projected
to exactly four fields (`account`, `direction`, `amount_minor`,
`leg_index`) with `leg_index` defaulting to 0. The array is then sorted
by `(account, direction, leg_index, amount_minor)`. Reordering the same
economic entries therefore never changes the fingerprint (verified in
self-test).

**Replay semantics of `post_ledger_transaction_v1`:**

- Existing row with the same `(event_type, event_id)` and the same
  fingerprint → returns the existing transaction id.
- Existing row with the same `(event_type, event_id)` and a different
  fingerprint → raises `SQLSTATE 23505` (idempotency-key conflict).
- Existing row inserted before Step 3 (fingerprint `NULL`) → treated as
  a match (defensive; only relevant to historical rows if any exist).
- Concurrent duplicate insert races the unique constraint; the
  `unique_violation` handler re-reads and replays only if the payload
  matches, otherwise re-raises.

## 8. Source-linked capacity model

`get_source_transfer_capacity_v1`:

- Reads only `stripe_source_transfer_events` for `event_kind =
  'transfer_created'` — reversals are audit-only and never restore
  capacity (per v7 §7).
- Fails closed if events for the charge are in a different currency
  than the caller supplies (`22023`).
- Fails closed if consumed > expected gross (`23514` over-capacity).
- Rejects null / non-positive / bad-currency arguments (`22004` / `22023`).
- Does not create a transfer. There is no Step 3 code path that inserts
  into `stripe_source_transfer_events`.

The underlying view has all Data-API grants revoked; only
`get_source_transfer_capacity_v1` (owner-executable) exposes derived
values.

## 14. Unresolved risks

1. **No posting from real webhooks yet.** The ledger primitives are
   ready but nothing calls them from Stripe webhook handlers. Step 4
   will introduce the webhook adapters and the reconciliation worker.
2. **Refund / dispute / transfer ingestion is not implemented.** Their
   catalogue entries and account codes exist and are validated, but the
   corresponding ingestion functions land in Step 5 (refund/dispute) and
   Step 6 (transfer execution).
3. **`SET CONSTRAINTS ALL IMMEDIATE`** inside a caller's transaction
   could still force early balance validation. All Step 3 primitives
   perform balance validation themselves before invoking the ledger
   primitive, so any such usage would only surface an
   already-detectable inconsistency earlier.
4. **Fingerprint is `NULL` for any historical ledger rows.** There are
   none today (`ledger_transactions` was created in Step 1 and never
   populated), but the replay path treats `NULL` fingerprints as
   matching — this is defensive and cannot lead to silent
   double-posting given the ledger tables were empty at the end of
   Step 2. A future step may backfill fingerprints deterministically.
5. **Audit-log write in classification is best-effort.** A failure to
   insert into `admin_audit_log` swallows the error and does not abort
   classification. This is intentional (auditing must never break a
   financial state transition) but means observability of classification
   activity depends on the audit table being writable.
